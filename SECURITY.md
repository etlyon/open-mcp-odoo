# Security

## Reporting a problem
Please report security problems **privately** to **contact@etlyon.com**, not in a public issue. We answer within a few working days and credit reporters who wish it.

## What the connector does to stay safe
- **Only the person's own server, only over https.** An address a person types is checked before anything is sent: https on port 443, a public host name (no IP literal, no user name or password in it, no query; for Hub, which v1 uses at the host root, a pasted page address keeps only its host); every resolved address must be public (no private, loopback, link-local, carrier-grade NAT, multicast or metadata ranges, including IPv6 forms embedding them). The connection goes to the checked IP itself with the real host name for TLS, so DNS cannot change in between. No redirects are followed and no proxy settings are read from the environment. Operators can also list hosts that must never be called, and can limit the connector to listed servers.
- **No master key.** Each connection's key is encrypted with its own random key, which is stored only wrapped by that connection's live tokens (kept only as hashes) or, during sign-in, by a key in the person's browser cookie. A copy of the database, the disk or a backup opens nothing. When a connection's last token expires (30 days without use) its key can no longer be opened and is deleted.
- **Sign-in.** OAuth 2.1 with PKCE (S256), exact redirect addresses, the token bound to one connector address (resource indicator), `iss` on every authorization response, one-time codes, rotating refresh tokens with reuse detection, revocation = disconnect. Assistants we cannot verify see their return address and must be explicitly allowed; the operator can refuse them entirely.
- **Pages.** No script; strict Content-Security-Policy; no framing; CSRF token, a browser-bound cookie and a same-site check on every form.
- **Hub (Nextcloud).** Only the person's own server: the address check, the login flow, the poll and every tool call go to the host the person typed, through the same guarded road. Of Nextcloud's login-flow answer the connector keeps only two tokens (strict pattern) and rebuilds both the approval address and the poll address from the checked server; a poll address on another host is refused, and the `server` field of the final answer is ignored. The poll token (whoever holds it receives the app password) is kept only encrypted under the person's browser cookie, never in the page or the logs. Each connection gets an app password of its own, named "Assistant connector" in Nextcloud, stored like an Odoo key, and deleted in Nextcloud on disconnect (revocation, also with an expired token), when the assistant's code exchange is refused, and at once when a sign-in is cancelled or its server changed after Nextcloud granted it (always on the server that granted it, never on another; a person who clicked Grant access a moment before leaving, or before pasting an app password instead, is covered too: the connector asks once more and deletes what it gets). A pasted app password is the person's own and is never deleted on cancel. Sign-ins waiting on one server share its poll budget fairly and no budget for starting them is shared, so nobody can block another person's sign-in. WebDAV answers and document XML are read only without a document type (in any encoding), so no entity is ever expanded. Write keys, confirmations and the one-search-at-a-time rule belong to one connection, never shared between people.
- **Tools never read files from the connector's machine** on a caller's request; attachments travel only as bytes (a test scans the source to keep it so).

## Residual risks the operator should know
- A connector reachable from the internet is a way to reach the servers people type. Keep the egress firewall of the host tight and use the denied-hosts setting for your own internal services that have public names.
- **Device-flow phishing (Hub).** Nextcloud's approval page is a plain link. Someone could start a sign-in on a connector they control and send a person that link; a person who then clicks Grant access gives that app password away. Nextcloud's page names the app asking ("Assistant connector"); people should grant access only from a page they opened themselves, in their own assistant. The connect window never asks anyone to send the link on.
- An app password whose connection expired unused (30 days) can no longer be opened by anyone, so the connector cannot delete it in Nextcloud; it stays listed under *Settings › Security*, where the person can delete it. The same holds for an app password from a sign-in the person left without *Not now* (the window closed, or Grant access clicked only afterwards).
- A person who is tricked into adding a look-alike connector address and pastes their key there gives that key away; the connect window always shows the server name and the assistant asking.
